The DEEDEV special case

Last time DEEDEV was rejected: "order price higher than the upper circuit limit." The stock was at its daily up-limit.

In the order ticket, Kite shows the price band (e.g. "Circuit: 585.00 – 650.75").
Place a LIMIT order with price = the upper circuit number or ₹1 below it.
If the stock is frozen at upper circuit, you likely won't get filled today — try tomorrow, or just skip it. It's ₹650 out of ₹1,00,000. Missing one name of 30 is immaterial.
After you finish buying — one required command

This is the important part. The bot keeps a file, .trading_state/momentum.json, listing which stocks it "owns." Right now that file only knows about GVPIL and TDPOWERSYS (from the Sep 2 partial run). If you buy the other 28 by hand, the file won't know — and next month the bot would try to buy them all over again, because it thinks you hold 0.

I added a small script to fix that. Run it once, after you're done placing orders:

That marks all 30 names as bot-owned. (It doesn't record share counts — the bot reads those live from Kite next run. It just says "these names are mine, not personal holdings.") It's safe even for names you skipped: the bot checks your real holdings and ignores names you don't actually hold.

PART 2 — How the automatic rebalance works from next month
What the script actually does

./scripts/run_local_rebalance.sh (with EXECUTION_MODE=live in .env) runs this sequence:

git pull — fetches any new signal files committed from your research machine.
Reads from Kite: your current holdings, live prices, available cash.
Computes the difference between what you hold and the new target list:
names that dropped out of the top ~45 → SELL
names that entered the top 30 → BUY
existing names that drifted → resize
Caps the trading at 20% of capital per month (the turnover cap — deliberate, matches the backtest). So it does not churn the whole portfolio each month.
Places orders: all sells first, then buys. If any sell errors, it skips all buys that run (safety).
Writes a receipt to receipts/ and updates .trading_state/momentum.json.

It will not bootstrap again — that only happens on a truly fresh account. From now on it's the gentle 20%/month rebalance.

"Will it automatically rebalance for me?" — Yes, but only if 4 things are true
#	Requirement	What happens if it's missing	How you satisfy it
1	A new signal file with a new date (e.g. 2026-09-30) is committed	Script sees the old Aug-31 file → refuses ("already submitted" / "stale"). Nothing trades.	Someone runs scripts/export_from_research.py on the research machine each month and git pushes the 4 artifact files. The script's git pull then picks them up.
2	Fresh Kite access token	Every API call fails. Nothing trades.	Run .venv/bin/python scripts/auth_kite.py and log in via browser the morning of the run. Tokens die every day around 7:30 AM IST.
3	Your machine's public IP is whitelisted in the Kite developer console	The "No IPs configured" error you're hitting now. Nothing trades.	Fix it when your lockout ends. Note: home internet IPs change periodically, so this can break again — a cloud VM with a fixed IP is the durable fix.
4	State file reconciled (mark_managed.py after any manual trading)	Bot re-buys names you already hold, or won't sell names it should.	The command in Part 1.

If all 4 hold, then one command does the whole rebalance. You still must then open the receipt and the Kite order book to confirm what actually filled (see Part 3).

What "automatic" does NOT mean
It does not refresh your token — you do that.
It does not generate new signals — the research export does.
It does not handle rejected orders — it logs them and moves on.
A cron job can run the command on a schedule, but it can't do the three things above. Realistically this is a monthly 10-minute manual routine, not a fire-and-forget robot.

PART 3 — When an order is rejected next time

Same behaviour as I described earlier:

"Submitted" ≠ "filled." The receipt only means Kite accepted the request. Always check the order book for the actual fill price and quantity.
A rejected BUY (circuit limit, price band, etc.) → the script logs it in the receipt and moves to the next order. That name is simply not bought this cycle. It's re-attempted next month automatically. No action needed unless you want to place it by hand.
A rejected SELL → the script skips every buy for the rest of that run (it won't spend cash it failed to raise). You'd re-run after fixing the cause.
Insufficient cash → caught before any order is placed; the whole run aborts with a clear message.
The script never retries or re-prices automatically.
